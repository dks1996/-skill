# 改造原理与定制指南

## 改造前后对比

改造前（常见默认骨架）：
```
File → IF/ELSE(按扩展名) → 提取器A / 提取器B → 聚合器 → 分段器 → 知识库
```
问题：分段器引用未初始化的共享变量；没有清洗，PDF 碎片原样入库；上传时逼用户手填参数。

改造后：
```
File → IF/ELSE(按扩展名) → 内置文档提取器 → 聚合器 → 智能清洗器(Code) → 分段器(固定参数) → 知识库
```
效果：识别类型 → 修碎片 → 规范空白 → 补主体前缀 → 固定分段 → 入库，全程无人值守。

## 智能清洗器做了什么

清洗器是一段放进 Dify Code 节点的 Python，只依赖标准库 `re` / `json`，分四步：

1. **修复碎片**：若一堆行里超过一半是 ≤3 字符的短行（典型 PDF 逐字符解析），依次拼接成段落，累计到设定长度断行。
2. **通用规范化**：去 `\r`、去行尾空白、压缩连续空行和空格、去掉"第 X 页/共 Y 页"和孤立页码。
3. **类型识别**：按 `clean_rules.types[].keywords` 在正文中匹配，命中即认定类型（征信 / 招标 / 合同 / …）。
4. **主体前缀**：对 `add_subject_prefix=true` 的类型，用正则从正文抽取主体名，按 `prefix_template` 生成前缀插到开头。这一步很关键——检索片段里若没有主体名，模型明知内容属于谁也"不敢说"。

## 决策树

```
是否 Pipeline 类型知识库？
├─ 否 → 本技能不适用；可建议改建 Pipeline 知识库，或改单文档切片
└─ 是 → 是否已跑 inspect_pipeline.py 且关键节点全部识别？
    ├─ 否 → 先调 dify_client.discover() 的匹配规则
    └─ 是 → 跑 install_cleaner.py
        └─ 跑 verify_pipeline.py 验证
            ├─ 碎片合并成少量段落 → 完成
            └─ 分段仍异常 → 查 references/api_notes.md 四个踩坑
```

## 定制文档类型

编辑 `config.json` 的 `clean_rules.types`，每项字段：

| 字段 | 含义 | 示例 |
|---|---|---|
| `name` | 类型标识 | `invoice` |
| `label` | 中文名，用于前缀 | `发票` |
| `keywords` | 命中任一即认定该类型 | `["增值税发票","开票日期"]` |
| `add_subject_prefix` | 是否补主体前缀 | `false` |
| `subject_regex` | 抽取主体的正则（可选，有默认值） | 见示例文件 |
| `prefix_template` | 前缀模板，占位符 `{subject}` `{label}` | `"{subject}的{label}："` |

改完重跑 `install_cleaner.py`，幂等更新，不会重复插节点。

## 幂等性与安全

- `install_cleaner.py` 会先找已有「智能清洗器」，有则更新、无则新建，可反复运行。
- 脚本只改流水线草稿与发布状态，不删除任何已上传的文档。
- 真实业务文档（含敏感信息）不会被脚本读取；脚本只处理用户显式传入的测试文件。
- 建议在没有真实用户流量的时段首次发布，随后用 `verify_pipeline.py` 验证再放开使用。

## 已知边界

- 扫描版 PDF（图片无文字层）无法清洗，需先 OCR。
- 表格类内容（xlsx）清洗效果有限，主要靠分段参数控制。
- 主体前缀的正则对复杂版式未必命中，命中失败时用 `subject_label` 兜底值，不会报错。
